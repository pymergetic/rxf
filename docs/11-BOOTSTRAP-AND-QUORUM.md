# Bootstrap, verification, and trust

RXF separates the authority of an image from the tools that create and execute it. A toolchain may be replaced; accepted bytes and their validated object graph remain the subject of trust.

## Seed construction

The reference toolchain constructs a seed from typed models and native inputs, assigns deterministic IDs, validates the graph, packs canonical bytes, and records provenance. Repeating the same pinned inputs and recipes must produce the same result.

Generated native Code records the source, compiler identity, flags, architecture, ABI, environment, digest, and extraction recipe needed for reproducibility. Generated bytes are outputs, not handwritten authority.

## Independent checking

A checker parses bounds before following offsets, validates header and section integrity, verifies cells and indexes, checks typed references and semantic closure, validates target/ABI metadata, and refuses unknown mandatory features. Checking does not execute program Code.

Certification should use at least one path independent from the writer for critical layout and envelope invariants. Cross-tool or cross-language checkers can form a stronger quorum, but RXF does not require one privileged runtime.

## Activation

Activation selects a `RuntimeTarget`, compatible Code, explicit imports, and capability providers; plans memory mapping and runtime tables; applies supported relocations; and transfers control through envelope-specific startup code. Planning data is not permission to exceed mapped or committed bounds.

Raw RXF need not be directly bootable by every platform. ELF, PE/COFF, and BIOS envelopes provide minimal loading glue while retaining the complete recoverable image.

## Successors

A successor is constructed non-mutatingly from an accepted base generation. Retained objects preserve durable identity; new objects receive new IDs; omitted transient or tombstoned objects do not become accidental dangling targets. The candidate is checked before publication or activation.

## Trust policy

Signatures, policy, accepted compiler identities, capability grants, and resource limits belong to explicit deployment policy and typed metadata. They are not inferred from the machine, process, repository checkout, or network environment that happens to open the file.
