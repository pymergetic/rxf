The model

The run-cell machine and the object model

How a suspended run, an arena cell, and a Python object are the same thing. Every fact on this page cites its section of docs/20-EXECUTION-POLICY.md (S1–S11); the numbers in pin chips are read out of the C in tests/host/ and are pinned by tests/test_model_doc.py — change the C and the test fails until this page is updated.

One rule runs through all of it: suspension is a data property. A suspended run is a cell in state PARKED S2. No thread, stack, register, or future belongs to a run. What suspends is data; what resumes is any carrier that reads that data.

Part 1 · S1 S2 S3

The substrate: one arena of cells

Everything the machine touches is a cell in one cell stream: objects, runs, the ready-ring, channel frames, the named roots of the world. The arena moves cells and hands out handles; a claim word per slot bounds how long any address stays valid. A run is a cell — its payload is smp_run_payload, and nothing of the run names the thing that executes it S1 S2.

Run cells

A run cell is a cell whose payload is smp_run_payload: the state machine, the wake token, the handles of what the run reads, and the whole volatile state of its program between two safe points S1. The proof's cells carry kinds of their own — every cell in the stream is one of these:

In a static image you meet a run cell's neighbours: the programs a run carries (Function and Code cells) and the channel frames it parks on. The run cell itself appears in a live world — and even then you cannot see a thread in it, only data.

The run-cell payload: three regions, and the boundary is the law

Checksum words, pinned to tests/host/smp_sched.c: prime 0x100000001B3, basis 0xcbf29ce484222325. A step that finds the checksum wrong counts checksum_fails and does not trust the state S1.

Object cells

A Python heap object is an arena cell — there is no second heap S11. What the interpreter holds is never the cell's address but a REPR A word that names it by handle and is resolved at use. The inspector's object detail is exactly this cell: header words, payload, and reference rows.

Named cells

The roots of the running world are named cells under the root: mp_state_ctx and its globals, the qstr pools, module registries — one name, one cell, handles resolved at use S11. The GC heap is not a special case: it is the arena S11. In this inspector, the named cells are the objects you see directly under the root — click one and the In the model card links here.

Part 2 · S7 S11

The two object faces

Two faces meet at a cell: the run's face (a handle: index | generation, never a raw address across a safe point) and the Python-heap face (REPR A: a tagged word that is a small int or a shifted handle). Both refuse the same thing: a name that outlived what it named.

Handles: index | generation

A handle names a cell as slot index in the low 32 bits and the slot's generation in the high 32 — generation << 32. Slots are handed out again when a cell is freed, so the generation changes on every reuse. A handle kept across a free is stale: it resolves to nothing and is refused. It never names the new cell of the same slot S7. Slot 0 is never handed out, so the all-zero handle is invalid everywhere; it is the HANDLE_NONE of the proof.

The live detail view shows the two halves on the handle row — index and generation — and the generation word itself sits at offset 24 of the cell header.

REPR A: the Python-heap face

REPR A is the word a Python value is in this machine S11: bit 0 set is a small int and needs no cell; otherwise the word is handle << 1, resolved at use. A cached object reference across a safe point is therefore a handle twice over — and a raw pointer may not outlive its step.

Stale names and ABA

The classic bug is a queue holding an old name for a slot that has been recycled. The machine refuses it structurally: the pop of the ready-ring checks each handle it takes out — a handle whose slot generation moved or whose slot is free is refused (ring_stale_refused) and the pop goes on to the next entry S3. A resolve of a stale handle is refused the same way (handle_stale_refused) S7.

Part 3 · S1 S3 S5 S7

The step lifecycle

Between the READY to RUNNING CAS and the next safe point, one carrier owns the program state of the run and is the only writer of it — run ownership is the only mutex in the machine S5. The handoff of ownership between carriers is the ready-ring; there is no handshake, no ack, no per-run lock.

The step loop

The state machine

Five states, each transition one CAS on the state word; a transition not in this table fails its CAS and changes nothing — the refusals are counted, not retried S1. The state names are pinned here:

A step answers the dispatcher one of four words — pinned here too: SMP_STEP_AGAIN = 0, SMP_STEP_PARK = 1, SMP_STEP_DONE = 2, SMP_STEP_SELFWAKE = 3.

Part 4 · S2 S4 S5 S8

Suspension, migration, compaction

What suspends is data, what resumes is any carrier that reads it. A parked run outlives whatever parked it; losing a carrier loses no runs S2.

Park and wake: the token protocol

No wake is ever lost and no run is enqueued twice. wake(run): store the waker and the wake token, attempt PARKED to READY; if the run was parked the enqueue into the ring is ours and the edge doorbell rings; if it was not parked the token stays for its next park and nothing else changes; if the ring refuses the push the wake is taken back with the one legal retreat (READY to PARKED, only before the enqueue). park(run): consume the token first — a wake that arrived while the run ran means the run does not sleep at all (SMP_STEP_SELFWAKE) S4.

Two runs wait on each other through a channel frame — itself a cell, held by handle, resolved at the start of a step and released before any park. The frame's head/tail words are the release/acquire edge that makes a word visible across carriers. The edge shim may wake a run but may never run it; timeout liveness is an edge concern and uses the same wake as any other waker S9.

Migration is observed, not performed

Resuming a run is a read of its cell, not a signal to an owner — so a run stepped by carrier 3 and then by carrier 7 needed no protocol. The only trace is evidence: park_carrier, resume_carrier, migrate_mask S5. The price is paid at safe points and only there: between two safe points the program state is owned and its addresses are valid; across a safe point nothing but handles survives S7.

Compaction under live runs

Runs execute while the arena is edited and compacted. The pass slides cells down in offset order, honoring pins: it claims a cell exclusively (CLAIM_MOVING = 0x80000000), writes C_FORWARD into the old header before the copy, copies the whole cell, publishes the new offset, releases the claim. A dead cell (kind 254) vanishes; a pinned cell keeps its source address; when the pass ends the vacated tail is filled with 0xA5 and ASAN-poisoned S8.

A claim is never held across a safe point, so the compactor waits at most one step for any cell (claim_spins) S5. A cell moved while its run is between safe points is legal and expected — the proof counts it as midflight_moved, and the run's next step simply resolves again.

The MicroPython seam

MicroPython's own safe points are the run cell's safe points. The seam is a mapping, two atomic words, and one rule: no GIL — ownership of the run cell is the only mutual exclusion S5.

Part 6 · S9 S10

What the proof pins

The result of a program is a function of the seed alone, whatever the interleaving S10: a step reads and writes its own run cell and its own data cell, and never the data of any other run. The differential runs the same program at one carrier and at eight, with compaction, deltas, and the deferral knob on and off — and the result words are byte-identical every time. The interleaving decides only who executes a step and when; that is read back as evidence and never mixed into the answer.

The harness writes 128 words of result and evidence (WIT_OUT_* of tests/host/smp_witness.h); words 0 to 2 are the answer and may not vary, the rest is evidence and may. The harness itself admits at most 32 carriers (RXF_SMP_MAX_CARRIERS), and the same binary is clean under AddressSanitizer/UBSan and under ThreadSanitizer.
