The teaching piece

The run-cell machine, stepped by hand

The model page documents the machine; this page makes you run it. Every scenario below is the machine of tests/host/smp_sched.c in miniature — one tick at a time, with the arena state and the carriers side by side. Nothing here is random: every schedule is fixed, so a screen always shows the same thing. The facts on this page are pinned as pin chips against the same sources the model page cites (tests/host/smp_*.h, core/ground.h, docs/20-EXECUTION-POLICY.md); tests/test_tutor.py fails if any of them drifts.

One rule runs through all of it: suspension is a data property S2. A suspended run is a cell in state PARKED — no thread, no stack, no future.

Part 1 · S1 S3 S5

The step-through simulator

Two runs, two carriers, one waker. Step tick by tick through claims, step seals, handoffs (RUNNING → PARKED CAS), checksum rewrites, parked and canceled states — and the two refusals the machine counts instead of retrying: a stale handle at the pop (ABA) S3 and a losing claim CAS. The arena cells with their header words sit on the left; the carriers and the event log on the right.

Part 2 · S4 S5 S10

The bugs as teaching examples

Two historical bugs, replayed. Toggle the buggy ordering, watch the failure appear on schedule; toggle it back and watch it disappear. The ordering is the only thing that changes between the two modes — the actors, the interleaving and the work are identical.

The seal after the CAS S5

The step seal (the step count and the FNV checksum rewrite) must happen inside the ownership window, before the handoff CAS. A waker may requeue a PARKED run the moment the CAS lands S4, and the next owner verifies the cell at once — so a seal after the CAS leaves the old owner writing while the new owner checks. That is the CHECKSUM_BAD flake, and it was a real leak.

The S4 compactor claim leak S4 S7

The channel sender resolves the frame and its data cell, finds its partner's cell being moved by the compactor (CLAIM_MOVING), and answers early. The rule is absolute: every claim goes back before the answer — the early return of the partner path included. A claim leaked there wedges the compactor's claim wait for good, because a claim is bounded only by the holder's next safe point S5.

Part 3 · S6 S10

Sync vs async, and the race detector

The same step sequence, run synchronously (all of C0's steps, then all of C1's) and async (the two carriers racing under schedules A–D). With the discipline of S6 — a step reads and writes its own run cell and its own data cell — the answer words are byte-identical in every interleaving: suspension is a data property, so the who and the when are evidence and never the answer S10. Break the discipline (one shared accumulator) and the race detector below lights up exactly where the interleaving changes the outcome.

the race detector

The answer words of each schedule, computed by the same engine, against the synchronous reference. Disciplined: every row is identical. Broken: the rows that differ are the interleavings that leaked into the answer.

Part 4 · S1 S2

The honest refusals

The machine refuses; it does not improvise. Trigger each refusal and watch the machine state that caused it — the refusal is named, counted, and the caller decides what happens next.

The codes are the interpreter's (native/graph.h): a call past the depth budget refuses RXF_REFUSE_CALL_DEPTH, a callee that names no bound program refuses RXF_REFUSE_UNBOUND. The cancel of docs/19 is not a code but a safe point: the break flag is data the poll finds, the step finishes, the seal lands, and the run ends there — no signal ever touched the run.

Part 5

Exercises

Five small ones. The checks are not memorized sentences: where possible the machine itself grades you — the engine runs the schedules and compares the words. One exercise per tab — the same .tabs component one level down, so no tab is an endless list.

1 · Order these two operations

A step is closing: it must seal the run cell (step count, checksum) and hand the run on with the cas (RUNNING → PARKED). Click them in the order the machine needs.

2 · Find the interleavings that break this

The shared-accumulator program of part 3, run under four schedules (words computed live; the sequential reference is B · C0 burst). Check every schedule whose answer words differ from the reference.

3 · Which of these runs is deterministic?

Three programs, each run under schedules A to D. Determinism is not a promise — it is the same answer every time.

4 · Name the refusal

A run's call depth is at 8 — the budget is spent — and the program makes one more call. What does the machine answer?
